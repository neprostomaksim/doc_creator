## 1. Что это за продукт

Веб-приложение для создания и редактирования договоров с клиентами.

**Кто пользуется:** предприниматели, юристы, тренеры и агентства, которые регулярно заключают
однотипные договоры. Закрытый сервис по приглашениям, в перспективе — SaaS.

**Проблема, которую решает:** сейчас человек копирует старый договор, вручную вычищает чужие
реквизиты, вставляет новые, следит за форматированием и рискует что-то забыть.

**Главное действие пользователя:** создать готовый .docx-договор с клиентом за пару минут —
с правильным оформлением, реквизитами обеих сторон, подписью и печатью.

**Язык интерфейса:** русский.

## 2. КЛЮЧЕВЫЕ АРХИТЕКТУРНЫЕ РЕШЕНИЯ

Это самая важная часть файла. Не отступай от этих решений без явного согласования.

### 2.1. Единая модель документа

Любой договор, каким бы способом он ни был создан, хранится как **структура блоков** (JSON),
а не как готовый текст и не как файл. Файл .docx — это результат рендеринга структуры.

```json
{
  "blocks": [
    { "id": "b1", "type": "title", "text": "ДОГОВОР ОКАЗАНИЯ УСЛУГ № {{contract_number}}" },
    { "id": "b2", "type": "paragraph", "text": "г. Минск, {{contract_date}}" },
    { "id": "b3", "type": "heading", "number": "1", "text": "ПРЕДМЕТ ДОГОВОРА" },
    { "id": "b4", "type": "clause", "number": "1.1", "text": "Исполнитель обязуется..." },
    { "id": "b5", "type": "list", "items": ["...", "..."] },
    { "id": "b6", "type": "table", "rows": [["Этап", "Срок"], ["...", "..."]] },
    { "id": "b7", "type": "requisites_table" },
    { "id": "b8", "type": "signatures" }
  ]
}
```

Допустимые `type`: `title`, `heading`, `paragraph`, `clause`, `list`, `table`,
`requisites_table`, `signatures`, `page_break`.

Блоки `requisites_table` и `signatures` — служебные: их содержимое подставляется рендерером
из реквизитов сторон и загруженных картинок подписи/печати.

### 2.2. .docx собирает КОД, а не ИИ

**ИИ никогда не генерирует файл.** ИИ работает только с текстом внутри блоков и со структурой
блоков. Превращение структуры в .docx делает исключительно код.

Причина: если просить ИИ выдавать документ целиком, форматирование будет плавать от генерации
к генерации, а печать некуда будет вставить.

Два пути рендеринга:
- **Есть исходный шаблон .docx** → подставляем значения в исходный файл с полным сохранением
  его оформления (библиотека `docx-templates`).
- **Документ строится с нуля** → собираем .docx из блоков программно (библиотека `docx`),
  применяя стили из настроек пользователя (шрифт, кегль, поля страницы, межстрочный интервал).

### 2.3. Три режима создания договора

Все три сводятся к одной механике — отличается только то, кто заполняет структуру блоков:

| Режим | Что происходит | Участвует ли ИИ |
|---|---|---|
| `strict` — строго по шаблону | Код подставляет данные в поля шаблона | Нет |
| `assisted` — шаблон + правки ИИ | Берём блоки шаблона, ИИ переписывает только указанные | Да, точечно |
| `generative` — с нуля | ИИ строит структуру блоков по примерам и материалам | Да, полностью |

Режим `strict` работает мгновенно, не стоит денег и не может «пофантазировать» в юридическом
тексте. Для типовых договоров это основной режим.

### 2.4. Гибкие реквизиты, а не жёсткие поля

Пользователи работают с разными странами (Беларусь — УНП, Россия — ИНН/КПП/ОГРН,
Польша — NIP/REGON). **Нельзя** прибивать колонки под конкретную страну.

Реквизиты хранятся как список пар «поле → значение» с сортировкой. Сверху — пресеты по странам,
которые просто предзаполняют этот список. Любое поле можно добавить, переименовать и удалить.

### 2.5. Дела и версии

Договор с клиентом — это не файл, а **дело** (папка), внутри которого живут версии v1, v2, v3.
Новая редакция создаётся копированием предыдущей версии с сохранением всех данных.

### 2.6. Блочный редактор, а не «Word в браузере»

Редактирование готового договора — это список блоков в духе Notion: каждый блок правится
отдельно. Полноценный WYSIWYG-редактор страницы А4 **не делаем** — это отдельный большой проект.
Предпросмотр итогового вида — отдельной кнопкой (рендер в .docx или в HTML-превью).

## 3. Стек

- **Фронтенд + бэкенд:** Next.js (App Router) + React + TypeScript.
- **Стили:** Tailwind CSS.
- **База, аутентификация, хранилище файлов:** Supabase.
- **ИИ:** Google Gemini API через `@google/genai`. Flash — для правок и разбора,
  Pro — для генерации с нуля.
- **Работа с .docx:**
  - `mammoth` — извлечение текста из загруженного шаблона для разбора на блоки;
  - `docx-templates` — подстановка данных в исходный .docx с сохранением оформления;
  - `docx` — сборка документа с нуля из блоков.
- **Хостинг:** Vercel.

### ВАЖНО: runtime

Всё, что работает с .docx, обязано выполняться в Node.js-окружении, а не в Edge.
В соответствующих route handlers явно указывай:

```ts
export const runtime = 'nodejs';
```

Иначе библиотеки для .docx не запустятся. Это одна из главных технических ловушек проекта.

### Секреты

Ключи (Supabase, Gemini) — только в переменных окружения (`.env.local`, в Vercel — Environment
Variables). Никогда не вставляй ключи в код и не коммить `.env.local`.

## 4. Структура данных

| Таблица | Поля |
|---|---|
| `profiles` | id, email, full_name, created_at |
| `invite_codes` | code, used_by, is_used, created_at |
| `organizations` | id, owner_id, name, country, logo_path — своя организация пользователя |
| `requisites` | id, owner_type ('organization' \| 'client'), owner_id, field_key, field_label, field_value, sort_order |
| `stamps` | id, user_id, name, type ('signature' \| 'stamp'), file_path |
| `clients` | id, user_id, name, country, contact_person, notes, created_at |
| `templates` | id, user_id, name, category, source_file_path, blocks (jsonb), fields (jsonb), doc_styles (jsonb) |
| `materials` | id, user_id, name, type, content_text, file_path, tags |
| `cases` | id, user_id, client_id, title, status ('draft' \| 'active' \| 'signed' \| 'archived'), created_at |
| `contract_versions` | id, case_id, version_number, mode, template_id, blocks (jsonb), data (jsonb), docx_path, created_at |
| `chat_messages` | id, version_id, role ('user' \| 'assistant'), content, created_at |

**Обязательно:** во всех таблицах — привязка к владельцу и включённый Row Level Security,
чтобы пользователь видел только свои данные. Закладываем многопользовательскую модель сразу,
даже пока пользователей мало.

**Хранилище файлов (Supabase Storage), приватные бакеты:**
`templates/`, `stamps/`, `materials/`, `contracts/`, `logos/`.

## 5. Экраны и навигация

Боковое меню слева (на мобильных — нижняя панель + выдвижное меню):

```
🏠 Дашборд
📄 Договоры
👥 Клиенты
📑 Шаблоны
📚 Материалы
⚙️ Настройки → Реквизиты · Подписи и печати · Профиль
```

**Главный сценарий:**
1. Вход → Дашборд с кнопкой «Создать договор».
2. Шаг 1 — выбор клиента (или создание нового прямо здесь).
3. Шаг 2 — выбор режима (strict / assisted / generative).
4. Шаг 3 — выбор шаблона, подключение материалов, разовая загрузка файлов.
5. Шаг 4 — заполнение полей (реквизиты клиента подтягиваются автоматически).
6. Генерация → редактор: слева блоки, справа чат с ИИ.
7. «Скачать .docx» → выбор подписи и печати → файл.
8. Договор автоматически попадает в дело клиента. Кнопка «Новая версия» копирует всё.

**Дашборд содержит:** последние 5 договоров с быстрым скачиванием, счётчики
(всего договоров / клиентов / за месяц), большую кнопку «Создать договор»,
блок «Черновики» (незавершённые генерации), «Частые клиенты».

## 6. Дизайн

Минималистичная эстетика в духе iOS 26: эффект матового стекла (backdrop-blur, полупрозрачные
поверхности, мягкие тени), скруглённые углы, спокойная нейтральная палитра с одним акцентным
цветом, крупные читаемые заголовки, щедрые отступы, плавные переходы.

Приоритет — удобство, а не эффекты. Стеклянные поверхности применяются к боковому меню,
карточкам и модальным окнам, но не к длинным текстам — читаемость важнее.

**Адаптивность обязательна на всех этапах**: приложение полностью работоспособно с телефона,
включая создание договоров. Верстку делай mobile-first.
